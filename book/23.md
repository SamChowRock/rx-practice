# 23｜每次查询都有回信，进度条怎么还会超时？

R7 的状态接口每两刻回一次「正在写，已写 1 行」。值班员看了半天，想知道是网络断了，还是生成文件的工作停在了第一行。两个问题需要看的记录不同。把同一个 `timeout` 挪过一个操作符，就能分别测出来。

## 秒表到底被谁重新按了一下？

沿用上一章的 `pollJob`。这次查询用一刻，回信后再等一刻。第 1、3、5、7 刻都会收到一份新对象，字段完全相同。直接订阅 `status.pipe(timeout({ each: 5 }))`，第 1 刻收到一项，期限移到 6；第 3 刻又收到一项，期限移到 8。它能发现“太久没收到消息”，这样的回信当然会让它一直等下去。

想测“太久没有进展”，先留下值得算作进展的状态。可为什么加了 `distinctUntilChanged()`，重复的回信还是全过了？在项目根目录运行 `node`：

```js
const { of, distinctUntilChanged } = require('rxjs')
const snapshots = of(
  { phase: 'writing', written: 1 },
  { phase: 'writing', written: 1 },
  { phase: 'writing', written: 2 },
  { phase: 'ready',   written: 2 }
)
snapshots.pipe(distinctUntilChanged()).subscribe(s => console.log(s.phase, s.written))
```

四条都打印了。每次取回的 JSON 都被解析成一个新对象；默认比较用 `===`，前两份即使字字相同也不相等。把比较函数写出来，才能告诉 RxJS 哪两个字段对这个进度条有意义：

```js
const sameProgress = (a, b) => a.phase === b.phase && a.written === b.written
snapshots.pipe(distinctUntilChanged(sameProgress))
  .subscribe(s => console.log(s.phase, s.written))
```

现在只打印 `writing 1`、`writing 2`、`ready 2`。比较函数返回 true 表示两份状态相同，这次可以跳过。若只比较行数，最后的 ready 也会被吞掉。上一章已经看到，写完最后一行和可以下载之间可能还隔着一次发布操作。

## 第 6 刻，服务器明明还在线

给 R7 单独开一次状态读取，再把去重后的流交给秒表。这里沿用上章的虚拟时钟，查询本身耗时一刻：

```ts
const status = pollJob(() => readStatus('R7'), 1, clock)
status.pipe(
  distinctUntilChanged(sameProgress),
  timeout({ each: 5, scheduler: clock })
)
```

第一份 `writing 1` 在第 1 刻通过，两份重复回信在第 3、5 刻被挡下。站在 `timeout` 的位置往回看，上一项仍然是第 1 刻，于是第 6 刻收到 `TimeoutError`，这份订阅连同它的轮询一起退出。如果把 `timeout` 写在去重之前，屏幕照样只画一次「1 行」，但重复回信一直在重设超时期限。只数渲染次数，分不出哪一种检测真的在工作。

`each: 5` 在没单独指定 `first` 时也管首项等待。这里的“进展”约定为同一个任务的阶段或已写行数发生变化，并且服务器保证行数不会倒退。若接口每次还带上不同的查询时间，把那个字段也拿来比较，每次心跳就又都会被当成进展。

## 如果承诺的是「六刻内可以下载」

再试一份确实有进展的回信。第 1 刻写到 1 行，第 5 刻写到 2 行，第 7 刻发布。相邻变化之间最长只隔四刻，五刻的停滞检测全程通过。可是从开始订阅到可以下载，一共用了七刻。

如果用户等的是下载按钮，`timeout({ first: 6 })` 前面就得只让能点亮按钮的值通过：

```ts
status.pipe(
  filter(s => s.phase === 'ready'),
  timeout({ first: 6, scheduler: clock })
)
```

第 5 刻那次更新可以显示在进度条上，但它进不了这条下载分支。等到第 6 刻仍没见过 ready，这里就会报错。若把 `first` 放在 `filter` 前面，第 1 刻的 writing 已经满足了首值期限。还有一个边界：如果上游提前正常完成却始终没发 ready，过滤后的流会直接空完成；要把“没有可下载文件”也报给界面，第 24 章会用到 `throwIfEmpty`。

运行 `npm run lab -- 23`。先看「回信到达」里的六个时刻，再对照「停滞超时」里的 6。第二轮把回信换成会前进的三步，能看到行数相同的 ready 被保留，而下载的总期限依然在 6 到期。实验里的时刻都从这份读取订阅时起算。[本章实验](../labs/23.ts)
