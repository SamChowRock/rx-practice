# 22｜只点了一次导出，服务器怎么建了两份报告？

上一章从 A 的两行和 B 的零行算出了对照结果。现在用户要下载这份报告。文件由服务器生成，可以先写 A 栏，再写 B 栏，最后才发布下载地址。点一次「导出」，服务器给一个任务号 R7。过一会儿再问进度，应该问的还是 R7。

这个接口有两种调用。创建任务会占一个新编号；查状态只读已有编号，每次返回一份状态就结束。要让面板持续更新，重复哪一次调用，直接决定了服务器的账本上有几笔任务。

## 先把两次调用印在终端里

在项目根目录运行 `node`。先让“创建任务”每次订阅都分配一个编号，“查状态”暂时只回显它查了谁：

```js
const { defer, of, switchMap, repeat } = require('rxjs')
let serial = 6
const create = defer(() => of('R' + ++serial))
const read = id => of('查 ' + id)

create.pipe(switchMap(read), repeat(2)).subscribe(console.log)
```

打印「查 R7」「查 R8」。`repeat(2)` 在它左边的来源正常完成后重新订阅，2 算上第一次，总共读两遍。左边包含 `create`，因此第二遍连分配编号的代码也重跑了。保留刚才的编号计数，换一下括号：

```js
create.pipe(switchMap(id => defer(() => read(id)).pipe(repeat(2))))
  .subscribe(console.log)
```

这回是「查 R9」「查 R9」。外层只创建一次；内层的工厂记住 R9，两次订阅都用它调用 `read`。这里数的是一次订阅。若按钮和进度条各自订阅整条包含 `create` 的管道，仍会创建两笔；让它们共用任务的办法和[第 20 章共读归档](20.md)一样。

如果 `read` 一调用就启动 fetch，`defer` 尤其重要：每次订阅要重新发查询，而同一个已经兑现的 Promise 可以被读很多遍，读到的始终是旧回信。

## 等这次回信，再约下一次

R7 到底要查几次，开始时谁也不知道。沿用上面的括号，只给状态查询加两条规则：每次回信并完成以后等两刻再查；看到 `ready`，把它交给下载按钮，然后结束。下面是[实验里两章共用的轮询函数](../labs/report-job.ts)的核心：

```ts
return defer(read).pipe(
  repeat({ delay: () => timer(pause, clock) }),
  takeWhile(status => status.phase !== 'ready', true),
)
```

`repeat` 收到一次查询的完成通知，会订阅 `delay` 返回的定时器。定时器发值，它才再次订阅 `defer(read)`。`takeWhile` 看到 `writing` 就继续，看到 `ready` 时条件首次为假。第二个参数 `true` 让这一条也通过，然后结束整段轮询。若省去它，服务器已经把报告发布了，按钮却收不到允许下载的那条状态。

接回导出按钮时，一次点击执行这段读取。这里的 `readStatus(id)` 每次只取一份状态；工厂记住创建时拿到的 id，所以定时器响几次都在查同一份报告。

```ts
const view = create.pipe(
  switchMap(id => pollJob(() => readStatus(id), 2, clock))
)
```

运行 `npm run lab -- 22`。实验用虚拟时钟让每次查询耗时三刻，一次查询在同一刻交付状态并完成：

| 发起查询 | 收到回信 | 面板看到的状态 | 下一次查询 |
|---|---|---|---|
| 0 | 3 | writing，已写 1 行 | 5 |
| 5 | 8 | writing，已写 2 行 | 10 |
| 10 | 13 | ready，仍是 2 行 | 轮询结束 |

第二条已经写满两行，文件还没发布。若按「写满两行就停」，第三条永远不会来。再试试在第 4 刻关窗：上次读取已经完成，此时订阅手里只有那只等到 5 的定时器。退订把它一起收走，请求记录里只剩第 0 刻的一次查询。服务器上已经创建的 R7 仍然存在。[本章实验](../labs/22.ts)

## 改成每两刻查一次呢？

写成 `timer(0, 2, clock).pipe(switchMap(() => read()))`，第 0 刻开始查，原本第 3 刻能回来。第 2 刻的节拍却先到了，`switchMap` 退出第一个读取并启动第二个；第二个原本第 5 刻能回来，又在第 4 刻被换掉。实验一直开到第 11 刻，已经启动六次，屏幕一条状态都没收到。这里的查询在退订时能撤掉自己的计时动作。

两种安排的区别只需看第 2 刻。固定节拍有权在那时启动下一轮；上面的 `repeat` 还在等第一轮结束。还有一种产品规则是每逢固定节拍都看看，若前一次没结束就跳过这拍。那才适合在节拍后用 `exhaustMap`。[第 6 章 · 一份工作还没结束时](06.md)
