# 24｜两个下载点，谁先交出能用的报告？

R7 已经发布，主站和镜像站各有一份，文件里写着「A:2 B:0」。用户只点一次下载，希望先到的那份立刻打开。主站在第 1 刻就回了响应头，第 8 刻才传完文件；镜像站第 3 刻回头部，第 5 刻已经传完。该在哪一刻停止另一边？

## 让两个下载点赛跑

这里把一次下载包装成 Observable。收到响应头，它会发一次 `headers`；正文读完，它才发 `file`，里面带着报告编号和文本。这样的接口既能显示连接进度，也能交付文件。第 10 章里的原生 `fromFetch(url)` 只会交出 Response，这里的第二次通知来自适配器继续读正文的那一步。[第 10 章 · 响应头和正文](10.md)

把两个下载点交给 `race(a, b)`，会得到一个跟随胜方的 Observable。RxJS 从接收到第一个 `next` 的来源继续取值，当场退订其他仍在竞争的来源。这里每次下载都稍后才回信，两边都来得及订上。在项目根目录运行 `node`，用两只 Subject 代两个站点：

```js
const { Subject, race } = require('rxjs')
const a = new Subject(), b = new Subject()
race(a, b).subscribe(e => console.log('收到', e))
a.next('主站头部')       // 第 1 刻
b.next('镜像头部')       // 第 3 刻
b.next('镜像文件 R7')    // 第 5 刻
a.next('主站文件 R7')    // 第 8 刻
a.complete()
```

只打印「主站头部」「主站文件 R7」。胜负在第 1 刻已经分出，到第 5 刻镜像文件抵达时，镜像那边的订阅早就退出了。哪怕你在 `race` 后面再过滤掉头部，也只能把胜方的头部从画面上藏起来。

如果两站都保证会成功，先在各自的来源里滤出完整文件，再用 `race`，就会由镜像在第 5 刻胜出。麻烦的是，镜像有时正在更新，可能只给旧版 R6；主站也可能先断线。用户愿意等另一边再试一次。

## 一处断线，为什么连另一处也等不到了？

留在刚才的提示符里。下面让主站在第 2 刻断线，镜像晚一些交 R7。这次回信已经简化成文件文本：

```js
const { catchError, EMPTY } = require('rxjs')
const primary = new Subject(), mirror = new Subject()
race(primary.pipe(catchError(() => EMPTY)), mirror).subscribe({
  next: text => console.log('文件', text),
  complete: () => console.log('结束')
})
primary.error(Error('断线'))
mirror.next('A:2 B:0')
```

实际只打印「结束」。`catchError` 把主站的异常换成了一个当场完成的空来源。在 RxJS 7.8.2，`race` 还没等到任何值时，有候选先完成，它会把完成传给下游，镜像也随订阅一起退出。保留原始 error 又会让整个竞争直接报错。这两种结束方式都比可用文件来得早。

## 只取第一份 R7

把需求拆回事件本身，就有另一条写法。两个来源各自把能交的 R7 文件送到同一个出口。某一路先交完空卷，出口继续等；有人交出一份合格文件，出口才关：

```ts
type ReportFile = { kind: 'file'; reportId: string; text: string }
type Transfer = { kind: 'headers' } | ReportFile

function filesFrom(source: Observable<Transfer>, reportId: string) {
  return source.pipe(
    filter((event): event is ReportFile =>
      event.kind === 'file' && event.reportId === reportId),
    map(file => file.text),
    catchError(() => EMPTY),
  )
}

const file = merge(filesFrom(a, 'R7'), filesFrom(b, 'R7')).pipe(
  take(1),
  throwIfEmpty(() => Error('两个下载点都没交付 R7')),
)
```

这里的 `Transfer` 只有头部和文件两种形状。谓词先检查 `kind`，因为只有文件才有 `reportId` 和 `text`。通过这两次检查的值才表示“正文已读完，而且属于本次导出”。类型标注让 TypeScript 知道下一行能读 `file.text`；运行时真正挡住 R6 的，是编号比较。

`merge` 会转发两路的值，一路正常完成时仍等另一路。假设主站第 2 刻断线，主站的 `catchError` 让这一路完成；镜像第 5 刻交出 R7，`take(1)` 把文本发给读者，完成下载订阅，剩余监听一起释放。如果把 `catchError` 移到 `merge` 外面，第 2 刻错误就会先结束整个合并，镜像仍来不及回信。对于真正的网络适配器，退订能省下多少传输，取决于它有没有把清理接到尚在读取的响应正文。

最后还有一笔账要对。主站断线，镜像只给了 R6 随后也完成，两路都没能向 `take(1)` 交值。`take(1)` 自己可以无值完成，`throwIfEmpty` 在这个时刻才把“没有拿到文件”变成错误。如果镜像一直沉默又不完成，两路还没全部结束，这个错误也不会出现。需要限制总下载时长时，可以像上一章那样，给合并后的合格文件设置首值期限。

运行 `npm run lab -- 24`。实验用同一组时刻比较两种写法，除了文件到达时间，还检查主站与镜像的订阅区间。直接赛跑时，镜像在第 1 刻退出；只取合格文件时，两路都留到第 5 刻。再把先回的一路换成断线或 R6，另一路仍然可以交付 R7。[本章实验](../labs/24.ts)
