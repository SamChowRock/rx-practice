## 接星星

双击本目录的 [play.html](play.html)，点「开始游戏」。轻点方向键换一轨，按住连续移动。接住一颗得 1 分，漏掉三颗就结束。页面已包含 RxJS 7.8.2，可以离线玩。默认打开完整游戏；第一节用的是右上角的「移动接收器」。

在控制台里，日志到达和点击导出是两件独立的事。到了游戏里也一样：按键要立即移动接收器，落星要等下一拍。两种动作共用同一个轨道位置，一次压线移动能不能得分，就取决于它们谁先发生。

| 小节 | 打开游戏时选择 | 这一关发生了什么 |
|---|---|---|
| [一 · 让接收器动起来](01-input.md) | 移动接收器 | 两次落星之间轻点，接收器仍会走一步 |
| [二 · 接住第一颗星](02-collision.md) | 第一颗星 | 星到落点的前一刻还能换轨 |
| [三 · 让一局游戏成立](03-round.md) | 完整一局 | 画面和计分牌看见同一颗随机生成的星 |
| [四 · 暂停、继续、再来一局](04-lifetime.md) | 暂停与重开 | 暂停留住场上的星，重开时清空 |
| [五 · 用虚拟时间验收](05-time.md) | 固定轨道验收 | 第三次漏接的那一拍，时钟就停 |

### 接星星的源码和实验

[game.ts](game.ts) 定义一拍的规则和整局的流。[main.ts](main.ts) 把浏览器事件接进来，并把状态画出来。五关共用这两个文件，通过关卡选择逐项开放规则。每节的实验都能在浏览器里观察，涉及精确时间的结论还可以在 [game.test.ts](game.test.ts) 复核。

修改源码时，使用课程现有的 Node.js 24+ 环境和依赖。在**项目根目录**运行：

```sh
node --test game/game.test.ts
node_modules/.bin/tsc -p game
node game/build.mjs
```

第三条命令用项目已有的 esbuild 将两款游戏的源码与 RxJS 分别打包进各自的 play.html。刷新已打开的游戏即可看到修改。只想玩或阅读时，直接打开成品即可。

## 雾港引航

打开[雾港引航](harbor/play.html)，选「缓潮」，点「启航」。留意右边信号台上的指针。第一座航标接近时，指针会从左往右走，进绿区按空格得 100 分，进中央金区得 150 分。你也可以点「点灯」。每座航标只结算一次，第三次失误就会迷航。

接星星时，我们数的是落了几拍。开船时换个问题：**上一帧指针还在绿区外，你按键时它刚好越过边界，这一盏该得几分？** 沿着这一次按键走一遍，就能看出 RxJS 和游戏规则各负责哪一步。

### 在两帧之间点灯

缓潮全程 22500 毫秒，第一座航标在航程的 15%，船在第 3375 毫秒经过标心。允许早到或晚到 590 毫秒，所以绿区的左边界是第 2785 毫秒。假设浏览器在第 2784 毫秒画了一帧，两毫秒后收到按键。拿上一帧的位置判，会算成「信号过早」。按游戏记录这次输入的时刻算，第 2786 毫秒已经进圈，该得 100 分。

怎么让两种事件都能及时改变船的位置？浏览器入口用 `animationFrames()` 接每次刷新，用 `fromEvent` 接按键和点击。按空格和点按钮都可以发出同一个点灯信号 `flash$`。下面摘出航行中的两路输入，`now()` 在页面里读的是 `performance.now()`。

```ts
merge(
  frames.pipe(map(() => ({ type: 'frame', now: now() }))),
  flash.pipe(map(() => ({ type: 'flash', now: now() }))),
)
```

`map` 给每个事件记下种类和时间。`merge` 同时订阅两路，哪一路先到就把那一个动作往下交。这样，即使下一帧还没来，点灯也能单独触发一次计算。下游的 `scan(advance, initial(mode))` 保存上一份状态，收到动作就调用 `advance(上一份状态, 动作)`，把返回的新状态交给画面，也留下来给下一个动作使用。

用刚才的数字走一遍。上一份状态记着航行了 2784 毫秒。点灯动作又带来 2 毫秒，`advance` 先把航程推到 2786，再算出距标心还有 589 毫秒，于是点亮第一座航标。下一帧接到的状态已经有了这 100 分，正在等第二座航标。时间和判分都可以单独验证。在装好依赖的项目根目录运行 `node`，把下面一段粘进去：

```js
const { advance, initial } = await import('./game/harbor/game.ts')
const start = advance(initial('calm'), { type: 'resume', now: 0 })
const before = advance(start, { type: 'frame', now: 2784 })
for (const now of [2784, 2785, 2786, 3180]) {
  const s = advance(before, { type: 'flash', now })
  console.log(now, s.marks[0], s.score)
}
```

四次都从同一份 `before` 出发，相当于重试同一盏灯。你会依次看到 `miss 0`、`lit 100`、`lit 100`、`perfect 150`。最后一次距标心恰好 195 毫秒，压在金区边上。可以把 3180 改为 3179，先猜分数，再跑一次循环。

### 暂停时，哪段时间算航程？

再开一局，在第一座航标前按 **P**，等五秒再按 **P**。假如把「现在减去启航时刻」当作船的航程，这五秒就足够让船越过第一座航标。游戏里的船会从暂停处继续。这里要保留两个不同的数：已经航行了多久（`elapsed`），以及上一次从浏览器读到的时刻（`last`）。

假设从时刻 0 启航，在 2000 毫秒暂停，7000 毫秒继续。暂停动作先把航程结到 2000。恢复动作保留这段航程，把 `last` 改成 7000。下一帧若在 7016 到来，就只加 `7016 - 7000`，船已经航行 **2016 毫秒**。如果只停画面，或者恢复时忘了更新 `last`，都可能让船突然向前跳。

这也解释了 `switchMap` 和 `scan` 的位置。航行时，内层 `switchMap` 接上动画帧和点灯两路输入；暂停时，它退订这两路，换成只发一个暂停动作的 `of(...)`。保存航程的 `scan` 写在这次切换的外面，所以仍记得那 2000 毫秒。试着想象把 `scan` 挪进航行分支：每次恢复都会创建一次新订阅，连第一盏已经点亮的灯也要重新记。

### 重新启航时，谁收走旧时钟？

点亮第一盏灯，按 **P**，这回点「重新启航」。船回到西湾邮埠，第一盏灯也恢复为待通过。对照刚才的「继续」：这次连保存分数的 `scan` 都要换掉。所以启航信号接在更外面的一层 `switchMap` 上。一旦收到新启航，它先退订上一局，再用新难度和初始分数建立一局。抵港或第三次失误时，`takeWhile(仍在航行或暂停, true)` 中的 `true` 让最后一份状态也能送到画面，随后才结束本局订阅。去掉它，页面就收不到用来显示「已抵港」或「已迷航」的那份状态。

要检查时钟到底在哪一刻停，光看船静止还不够。退出刚才的 Node 提示符（输入 `.exit`），在项目根目录运行：

```sh
node --test game/harbor/game.test.ts
```

看「暂停和切到后台冻结航程」这条测试。它把浏览器时钟换成可以手动推进的 `TestScheduler`。第 4 毫秒模拟切到后台，第 6 毫秒发一次点灯，第 10 毫秒继续。测试既检查中间没有点灯产生的新状态，也检查时钟在第 4 毫秒退订、第 10 毫秒才重新订阅。这样，即使有人把暂停改成只让船停画、让时钟在后台空转，测试也能发现。

想改一条规则，可以打开 `game/harbor/game.ts`，把缓潮的 `perfect` 从 195 改成 100。在新的 Node 会话里重跑第一段实验：第 3180 毫秒仍在绿区，这次只得 100 分。运行 `node game/build.mjs`，刷新试玩页面，信号台中央的金区也会随之变窄。
